1. Introduction 
1.1 Document Purpose 
The Software Requirements Specification (SRS) is providing fully explicit and complete 
specification of a modularized AI/ML based multi-layered system for Phishing Detection and 
Prevention, which defines explicitly the:  
• Functional requirements 
• Non-functional requirements 
• boundaries and scope of the system 
• External interfaces  
• constraints on the operation of the system 
 
This is the authoritative reference document on the requirements of the system for all 
the stakeholders involved in the design, implementation, operation and maintenance of the 
system. It also forms the contractual and planning basis for estimating cost and resources, 
identifying risks, planning acceptance tests and tracing requirements. 
 
1.2 Product Scope 
The Real-Time AI/ML Based Phishing Detection and Prevention System is an intelligent 
security solution system capable of identifying, categorizing, and stopping phishing threats live: 
 
It offers security for all of the following: 
• email communications 
• URLs & clickable links 
• Web sessions 
• suspect password collection web pages 
 
It integrates machine learning, natural language processing (NLP), behavioural analytics, and 
protection at the browser level for proactive counter-measures. 
The platform runs with three different integrated elements backed by a protected backend 
infrastructure: 
• Browsers Extension - Online scan of URLs and web pages along with instantaneous alert 
systems 
• AI/ML threat analysis engine (backend) - Categorization of URLs, email content analysis, 
pattern recognition, and processing of threat scores 
• Administration dashboard - aggregated monitoring, analytics, forensic reporting, and 
threat intelligence platform

The system is designed to identify and process:

1.4 Definitions, Acronyms, and Abbreviations 
The definitions used in this document are as follows: 
• AI. Artificial Intelligence: Program that automates tasks of human brains such as 
recognizing patterns or tackling decision problems. 
• ML. Machine Learning: One of AI's particular areas-The process remains the same, 
incrementing it with more useful knowledge; it no longer necessitated to program it 
element by element. 
• NLP . Natural Language Processing: A sub-part of AI used for recognizing language in the 
form of text in order to detect phishing language. 
• API. Application Programming Interface: A set of protocols for enabling communication 
between the browser extension, backend engine, and user dashboard. 
• Phishing: An attack technique where deception is used to extract sensitive information 
from the user. The information is usually acquired through messages or webpages. 
• Zero Day: A previously un-defended against phishing attack that evades all rule set 
comparison detection methods. 
• Threat Score: A number which expresses the likelihood that a URL/email/webpage is 
malicious. 
• Domain Similarity Detection: Technique for detecting similar but 'spoofed' domain 
names paypa1.com/paipai.com etc. 
• Credential stealing form: Webpage form used to obtain user id, password, credit card 
number etc. 
• SSL (Secure Sockets Layer): Conversation exchanged between components of the system 
by SSL encryption. 
• JSON (JavaScript Object Notation): Lightweight data format, used in API communication. 
• WebSocket: Protocol for communicating system information in real-time channel both 
ways (server-space to client-space and vice-versa). 
• Latency: The time difference between URL/email submission and threat classification 
output. 
• Near Real-Time: Process identified in less than 1-3 seconds.

2. Overall Description 
2.1 Problem Statement 
Phishing emerged as most common and one of the costliest categories of cybercrime. 
Attackers leverage advancements in technologies like AI for sending domain-faking emails, 
credential gathering sites and emails, etc. 
 
Most of the existing solutions are based on static rule-based detection, blacklisting, 
cookie tracking, pattern matching etc. These are suboptimal solutions because: 
• Do not cover zero-day attacks, blacklisted sites quickly get re-published as spammers, 
hackers every now and then. 
• Are not able to integrate threat intelligence quickly enough. 
• Are not able to prevent AI generated emails or sense context-aware phishing emails. 
• Provide limited visibility across access in a browser. 
 
Blind to subtle clues in a phishing attack such as: 
look alike domain names (paypa1.com), messages urging to take urgent action, fake 
login screens, URL shorteners, encapsulated URL frames etc. 
 
More so organizations are faced with: 
Tons of incoming email, inability to handle response, no visibility within threat landscape 
and threats of credential theft, financial loses and information leaks. 
 
The Real-Time AI/ML-Based Phishing Detection and Prevention System solves these 
problems with continuous threat monitoring and input, real-time threat scoring, behavioural 
and pattern-based threat detection, browser-based threat detection, centralized administration.

The system delivers AI powered phishing detection for end-users and security teams.

Automatic deep scanning of all visited links Phishing warning on suspicious URLs (

Connection of input email messages with URLs in the message body Ped, embedded, 
hidden links to either recognize phishing sites, identify malware payload, or put forward the 
true message URL classifier of email content based on Natural Language Processing (NLP) 
techniques of: Requests for sensitive information Impersonation Or combinations of both 
Expressions of urgency (Why they want x now) Requests for credentials Classifier of email as: 
safe, suspicious, and phishing Webpage content inspection

Fake login pages Monitor displays of input fields SSL verification Inspection of web

2.3.4 Persistent Browser Protection Detection of phishing 
Content, behaviour & URL instantly provides the user with a restaurant suggestion, and 
if user encounters a phishing threat the system instantly blocks the user from visiting the

and the system will no longer visit such website. At the same time individual browser settings 
will be made and associated web browser behaviour will be modified and run automatically 
whitelisting the frequency of visiting such websites.

3.2 Functional Requirements 
Each requirement is uniquely labelled. 
1. FR-1: URL Interception 
The system shall intercept URLs visited by users through the browser extension 
before or during page loading for security analysis. 

17  
  
 
 
2. FR-2: URL Feature Extraction 
The system shall extract structural and lexical features from URLs, including 
domain name, subdomain patterns, path length, and suspicious character usage. 
3. FR-3: Domain Similarity Detection 
The system shall analyse domain similarity against known legitimate domains 
using string comparison techniques to detect look-alike phishing domains. 
4. FR-4: SSL and Certificate Validation 
The system shall verify the presence and validity of SSL certificates and flag 
invalid or suspicious certificates. 
5. FR-5: Webpage Content Analysis 
The system shall analyse webpage content for phishing indicators including: 
• Credential input fields 
• Suspicious form actions 
• Urgency-based language 
• Brand impersonation patterns 
6. FR-6: Email Content Classification 
The system shall classify email content using NLP techniques to identify phishing 
characteristics. 
7. FR-7: Threat Scoring  
The system shall assign a numerical threat score to each analysed URL or email 
and classify it as: 
• Safe 
• Suspicious 
• Phishing 
8. FR-8: Real-Time User Alerting 
The system shall display real-time warnings to users when a phishing threat is 
detected. 
9. FR-9: Access Blocking 
The system shall block access to URLs classified as confirmed phishing unless 
explicitly overridden by the user (configurable). 
10. FR-10: Zero-Day Detection 
The system shall detect previously unseen phishing URLs based on learned 
behavioural patterns without reliance solely on static blacklists. 
11. FR-11: Incident Logging 
The system shall log all detected phishing incidents with timestamp, threat score, 
classification, and relevant metadata. 
12. FR-12: Administrative Monitoring 
The system shall provide administrators with real-time visibility of phishing 
incidents across the organization. 
13. FR-13: Historical Threat Data Retention 

18  
  
 
 
The system shall retain phishing detection logs for a minimum configurable 
retention period (e.g., 90 days). 
14. FR-14: Model Retraining Support 
The system shall support periodic retraining of machine learning models using 
updated datasets. 
15. FR-15: Configurable Detection Threshold 
The system shall allow administrators to configure threat score thresholds that 
determine classification levels. 
16. FR-16: Role-Based Access Control 
The system shall restrict administrative functions based on user roles and 
permissions. 
17. FR-17: Secure Authentication 
The system shall require secure authentication for administrative access using 
encrypted credentials. 
 
18. FR-18: Performance Logging 
The system shall track detection accuracy metrics including false positives and 
false negatives. 
19. FR-19: Reporting and Export 
The system shall allow administrators to generate and export phishing incident 
reports. 
20. FR-20: System Health Monitoring 
The system shall monitor server uptime, API performance, and model inference 
latency. 
 
3.3 Use Case Model 
3.3.1 Use Case 1: User Visits a Suspicious Website 
Actor: End User 
Preconditions: Browser extension installed and active. 
Main Flow: 
• The user enters a URL in the browser. 
• The browser extension intercepts the URL. 
• The system sends the URL to the backend for analysis. 
• The ML engine evaluates the URL and webpage content. 
• The system assigns a threat score. 
• If classified as phishing, a warning popup is displayed. 
• The user chooses to proceed or exit. 
Postconditions: The user is warned before interacting with a phishing site. 

19  
  
 
 
 
3.3.2 Use Case 2: Administrator Monitors Threat Activity 
Actor: Administrator 
Preconditions: Administrator is authenticated. 
Main Flow: 
• The administrator logs into the dashboard. 
• The system displays real-time phishing incidents. 
• The administrator filters incidents by date or risk level. 
• The administrator reviews detailed threat logs. 
• The administrator exports a report if needed. 
 
Postconditions: Administrator gains insight into threat landscape. 
 
3.3.3 Use Case 3: ML Model Update 
Actor: ML Engineer / System Admin 
Preconditions: New labelled dataset available. 
Main Flow: 
• Engineer uploads updated training dataset. 
• The system retrains the ML model. 
• Model evaluation metrics are generated. 
• If accuracy thresholds are met, model is deployed. 
• The system begins using updated model for inference. 
Postconditions: Improved detection performance. 
4. Other Non-Functional Requirements 
4.1 Performance Requirements 
Performance requirements define how efficiently, accurately, and responsively the 
phishing detection system must operate under varying load and network conditions. 
The system shall perform URL analysis and return a classification result within two 
seconds under normal network conditions. Under peak load, API response times shall remain 
below three seconds. 
The browser extension shall display initial risk indicators within one second of receiving 
the backend response, ensuring minimal browsing disruption. 
The administrative dashboard shall load its primary interface within five seconds on 
standard broadband connections. Subsequent actions such as filtering incidents, loading 
reports, or viewing detailed logs shall respond within two seconds. 
The backend shall support: 

20  
  
 
 
• At least 10,000 concurrent users 
• A minimum of 1,000 URL analysis requests per minute 
• Horizontal scalability to accommodate growth without degradation 
Machine learning inference shall maintain: 
• Average processing time per request below 1.5 seconds 
• Memory utilization within defined server resource limits 
• CPU usage optimized to prevent bottlenecks during peak activity 
Detection performance shall meet the following minimum targets: 
• Overall classification accuracy ≥ 90% 
• Precision ≥ 90% 
• Recall ≥ 85% 
• False positive rate ≤ 5% 
The system shall continuously monitor model performance metrics and log deviations 
from target thresholds. 
Bandwidth usage for browser-to-server communication shall be minimized: 
• Each analysis request payload shall not exceed 100 KB 
• Response payloads shall remain optimized and compressed where possible 
• The system shall degrade gracefully under heavy load, prioritizing real-time classification 
over historical data queries. 
4.2 Safety and Security Requirements 
Safety and security requirements ensure protection of user data, system integrity, and 
resilience against cyber threats. 
All communications between browser extension, backend server, and administrative 
dashboard shall use HTTPS with TLS 1.2 or higher. Unencrypted requests shall be rejected. 
Administrative access shall require: 
• Strong password enforcement 
• Multi-factor authentication (MFA) support (future-ready) 
• Account lockout after a configurable number of failed attempts 
• Automatic session expiration after inactivity 
The system shall implement: 
• Input validation and sanitization for all API inputs 
• Protection against SQL injection, XSS, CSRF, and command injection 
• API rate limiting to prevent abuse 
• Protection against denial-of-service attempts 
Administrative actions shall be logged in secure audit logs including: 
• User identifier 
• Timestamp 
• Action performed 
• IP address 
Audit logs shall be retained for a minimum of one year. 

21  
  
 
 
The system shall protect user privacy by: 
• Minimizing storage of personally identifiable information 
• Avoiding storage of raw passwords or sensitive form data 
• Not storing full webpage contents beyond analysis necessity 
• Encrypting stored sensitive metadata 
The system shall not analyse or store user data beyond phishing detection purposes without 
explicit authorization. 
To prevent model exploitation, the system shall: 
• Limit exposure of internal ML model architecture 
• Prevent adversarial query patterns 
• Monitor abnormal repeated classification requests
